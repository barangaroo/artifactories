# MCP operational outcomes

This instrumentation is an implementation capability, not a claim that it is enabled on the deployed service. It does not measure agent activation or usefulness. Use the private cohort evidence workflow for those outcomes.

## Enable and disable

The built-in HTTP sink runs only when all three conditions hold:

- `NODE_ENV=production`
- `VERCEL_ENV=production`
- `MCP_TELEMETRY_ENABLED=true`

Unset the telemetry flag or set it to `false` to disable the sink. Preview, local development, and tests stay silent by default. Enabling production collection requires a separately authorized deployment/environment change; this engineering sprint did not do that.

The shared MCP package exposes an optional synchronous `onToolOutcome` observer. The HTTP handler supplies it; the stdio CLI does not. Observers receive only a fixed tool name, fixed outcome, and coarse duration bucket. A throwing observer cannot alter a tool result.

## What is measured

| Event family | Meaning | Limit |
| --- | --- | --- |
| `http_discover_*` | HTTP acceptance/rejection for modern `server/discover` | Not proof that a client completed negotiation |
| `http_initialize_*` | HTTP acceptance/rejection for legacy `initialize` | Not semantic JSON-RPC success |
| `http_other_accepted` | Other successful HTTP status | May contain a tool/JSON-RPC error |
| `http_method_rejected` | HTTP 405, including expected stateless-method rejection | Not automatically an outage |
| `http_boundary_rejected` | Host/origin guard rejected a request | Guards and authority are unchanged |
| `http_sdk_rejected_code_unavailable` | Other non-success HTTP status from SDK | No inferred JSON-RPC code |
| `jsonrpc_parse_error` / `jsonrpc_invalid_request` | Errors generated by our bounded body parser | Known codes -32700 / -32600 respectively |
| `http_unexpected_failure` | Handler exception or HTTP 5xx | No error messages or stacks collected here |
| `tool_*_empty/nonempty/error` | Adapter-backed tool callback outcome | SDK input/output validation and delivery are outside this observation |
| `tool_get_return_briefing_no_return/has_return/error` | Whether briefing calculation found candidate reasons | A candidate reason is neither permission to act nor evidence of usefulness |

Tool duration observations use `lt100`, `100to999`, and `gte1000` millisecond buckets. They cover adapter work and briefing calculation only, not SDK validation, serialization, network latency, or client consumption. Buckets are aggregated across tools; they are not per-tool percentiles.

SDK-rejected arguments and unknown tool names can fail before the callback runs. These do not generate callback outcome events. Response streams are never read or buffered for telemetry, so semantic failures outside the callback are not fully observable here.

## Bounded, partial aggregates

The log event is `artifactories_mcp_outcomes`, with `scope: "process_partial"` and `countsAsActivation: false`. It is emitted on the first observed event and then no more than once per minute per process, when another event arrives. Fixed-key counters and duration buckets are reset on emission; there are no background timers, extra database writes, or external collector calls.

This is best-effort operational evidence, not a durable census:

- A process's final pending interval can be lost when the process stops or is frozen.
- Cold starts can emit small first-event aggregates, so a fleet is not limited to one log line per minute globally.
- Sink failures are swallowed and that snapshot is discarded.
- HTTP events and tool events are different observations; do not add them together as requests.
- These aggregates do not establish a conversion funnel, unique clients, operators, or retained use.

Use Vercel request metrics for traffic totals and these counters to investigate callback outcomes. Do not combine their denominators as though collection were complete or identically scoped.

No message text, arguments, prompts, keys, proofs, IDs, cursors, user agents, IPs, arbitrary method names, or exception messages are emitted. Labels are allowlisted at runtime as well as typed. User-controlled data never changes authorization or telemetry cardinality.

## Local verification

`npm run mcp:test` verifies the optional observer with an official client against an in-process/loopback-only server, including empty/no-return results, callback errors, observer failures, and default silence. Root tests `tests/mcp-http.test.ts` and `tests/mcp-telemetry.test.ts` exercise transport classification, privacy boundaries, the production opt-in gate, and bounded logging. No public write tests are needed.
